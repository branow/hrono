Who writes what

Each stage calls the model configured for its role in Settings. Point the brief or brief-upper role at another model, or edit its prompt, and the briefs it wrote are rewritten the next time briefs are written; a new key for the same connection rewrites nothing. Settings says how many topics a change would redo, and roughly what that costs, before you save it, and can show what an edited prompt writes for one topic beside its current brief first.

What recall does

Recall answers a question with the passages most like it, and says where each came from. It embeds the question, ranks every passage and brief in the tree by how close it is, and returns up to {{ recall.cap }} of the closest, one per file.

It first checks that the tree has the words for the question: when fewer than {{ recall.coverage }}% of the question's words occur anywhere in the tree, it says {{ recall.refusal }} and hands over to the map, because the closest passage to a question the tree does not cover answers nothing. That is the design working, not a fault. Recall never calls a language model, so it costs nothing per question.

What export produces

A folder of Markdown an agent reads without hrono running: root.md first, then one link per level down to the source text. The stored tree can be deeper than an agent should have to walk, so the export flattens it to a hop limit, {{ export.hops }} by default, choosing the levels that keep the widest page shortest. A page aims to list at most {{ export.width }} topics, about as much to read as one section.

Export is built from what is stored, with no model call. It comes from the Export page as a zip, or from the command line with hrono tree export. Topics with no usable brief are listed there first, because an agent reads those pages first. The same page has a Connect an agent block: ready-to-paste commands for the command line, a curl call to recall, and the export, filled with this server and tree.

What it fixes by itself

This is the part the map does not show, and the part worth knowing before reading the map's overlays. A sync never regroups the whole corpus: it decides, per changed section, with plain arithmetic.

  • a file you did not touch Nothing happens. Its section cannot move; nothing recomputes it.
  • a file you edited Re-embedded, then compared against its own topic as it was. Still {{ rule.tau }} similar or better, it stays and only its own brief is rewritten. Below that, the content genuinely left the topic and it is placed again.
  • a file you renamed or moved Its section keeps its topic: the content is the same, so nothing is compared again.
  • a new file Placed in the topic whose centre it is closest to, if that is {{ rule.tau }} or better. If nothing is close enough it is parked. At the end of the sync, parked sections form a topic of their own if there are enough of them to be one; the rest are filed in the nearest topic anyway, marked as placed by force, so a later check can move them once similar sections arrive.
  • a topic past {{ rule.cap }} sections Splits itself. That cap is the summarization budget: above it, one brief cannot stay faithful to everything under it.
  • over {{ rule.misfit }}% misfits in one topic It sheds them, each to the topic that actually fits it. No one asks you.
  • a topic down to one section Dissolves; the survivor is placed again by the same rule as a new file.

What a sync does not do. When the whole tree has drifted, hrono tells you rather than acting. A run reports that a settle is due once the changes since the last one add up to {{ rule.churn }} drift points, or the share of misfits passes {{ rule.factor|round|int }} times what the first build measured. A settle regroups the whole tree and rewrites only the topics whose sections changed. It spends model calls, so you start it yourself from Runs.

A few misfits are normal, not a defect

Topics are not spheres, so sections at the edge of one always lean slightly toward the neighbour. A new tree always starts with some, and hrono keeps that first measurement as its baseline. The repairs above fire on thresholds — {{ rule.misfit }}% within one topic — precisely so that the normal residue is left alone. What the map's overlays draw is that residue: what automation looked at and decided was not worth a rebuild. They are a second opinion you can act on, never a queue you are expected to clear.

The three overlays on the map

Lines the tree itself cannot draw. Each answers one question and suggests one repair.

  • misfiled (pull)

    Which sections sit in the wrong topic? The arc runs from the topic holding them to the one they actually resemble, and says how many. Repair: move them.

  • near-duplicates (proximity)

    Did one subject get split across two topics? The arc joins two topics under the same parent that are nearly the same thing. Repair: merge them.

  • what a change touched (propagation)

    After a sync, which briefs did an edit force a rewrite of? A line runs from the topic whose content changed up to the highest brief marked for a rewrite. Nothing to repair — it is the receipt.

    On a tree that was built once and never re-synced there is nothing to draw, and the overlay turning on changes nothing. That is correct, not broken.

On a large tree the map draws only the strongest few arcs, and never one that would run through a topic's name. A topic with arcs left out says so beside its circle, as +3 arcs; click it to see that topic's arcs on their own.

What a pin does

Edit a topic by hand and the edit is pinned: the pipeline treats it as fixed and works around it. Three things can be held. A brief you rewrote is never regenerated. A section you filed under a topic is never moved by a repair. A topic you hung under a parent is never re-attached elsewhere. A rename and a note stay as you wrote them, too.

A pin lasts until you release it, on the topic page or from the list of hand edits on Health. A run reports how many hand edits it left alone, so you can see the pipeline respecting them.

Where the cost comes from

Only model calls cost anything, and only a few stages make them: one call to condense each new section, one to write each brief that needs writing, and a panel of {{ rule.panel }} judge calls for each changed topic. Reading the map, recall, ask, and export call no language model.

That is why a sync is cheap and a first build is not: a sync pays for what changed, a first build or a settle pays for everything it touches. A first build is maintain, and the Set up page says what it will cost before it starts: model calls, tokens, time and money, counted from the files it will read. A full rebuild from nothing is build-tree, which pays twice over. Home shows what the tree has spent and what the last run did. Each run's page shows its tokens, cost and model time, split by stage, and the Usage page adds them up by day, model, run and person (hrono usage does the same from a terminal). A run from before spend was recorded reads not recorded, never free. A model billed through a subscription is shown as an estimate, never as spend, and the two are never added.

Questions

If it repairs itself, why can I edit anything by hand?

Because grouping has no opinion about what matters to you. It can tell that two topics are similar; it cannot know that one of them is the thing your team calls "billing" and deserves its own name. A hand edit is pinned, which is what stops the next sync from undoing it — a correction that silently reverts is worse than no correction.

I changed one file. How much gets rewritten?

Its own topic's brief, always. Then the judge model is asked once about that topic, by a panel of {{ rule.panel }} with the majority deciding, whether the new content changes what its brief says. If the answer is no, nothing above it is touched, which is what happens to a typo. If it is yes, every brief above it is marked for a rewrite, up to {{ rule.climb }} levels, or to the root if that is nearer. The what a change touched overlay and the Activity page both show how far it went.

Why is my brief a question back to me instead of a summary?

A model was called in a context that made it answer the caller rather than summarise the material. Rewrite it by hand on the topic page — that pins it — or fix the cause and re-run. A reply that does not look like a brief is stored with a flag rather than dropped, because a flagged brief you can see beats a topic missing from the map.

Nothing happened when I re-ran a sync.

That is the design working. Condensations are keyed by content hash and briefs by their members' signature, so a re-run over unchanged sources makes no model calls. The exception is a stored reply that was not a real condensation or brief: those are tried again. If you expected work, check that the source actually fetched new commits on the Runs page.

What does a topic's "fit" number mean?

How close that section sits to the centre of the topic holding it, from 0 to 1; a section marked forced has no number because it was placed without one. Low is not wrong — the edges of a topic are where the interesting material usually is — it is only worth looking at when the misfiled overlay says something else is closer.

Can I have more than one tree?

Yes. A tree is a name plus the sources it maps, so one database can hold a tree per product, per team, or per question. Make one in Settings; the bar at the top switches between them.

Words

topic
A group of related sections, or of other topics, plus a brief. The unit the tree is made of.
section
About {{ limits.section|size }} of one file. What gets grouped, and what an agent reads when it explores.
condensation
What the first pass wrote about one section — identifiers verbatim, plus GOTCHA: lines. Cached by content, so an unchanged file is never condensed twice.
brief
A topic's summary, written from its condensations rather than from raw text. Reference lists are appended by code, never by the model.
passage
About {{ limits.passage|size }}. What recall injects. A section reassembles exactly from its passages.
tree
Topics all the way up to one root, over a named set of sources. A database can hold several.
stale
A brief that no longer matches what its topic holds — the members changed, or the prompt, or the model.
pin
A hand edit the pipeline must not undo. Pinning is what makes a correction survive the next run.
parked
A section ingested and embedded but in no topic yet. On the waiting list, not lost.
misfit
A section whose own topic's centre is not the nearest one. A few are normal.

Not used here: cluster is the algorithm's verb — what it makes is a topic. Chunk was an earlier name for a section. Node is the database's word for a topic. Paragraph is not a unit here: sections are cut by structure and size.
