# REST API and CLI

`hrono serve` is the only process that touches the database. The CLI and the
`/ui` dashboard are HTTP clients of it. Routes live in `src/hrono/server/`;
the collection CRUD routers are generated by `src/hrono/registry/engine.py`.

## Conventions

- **Config is data you PUT; work is a job you POST.** Writing config never
  starts work. Slow work returns `{"job_id": ...}` and runs on the background
  worker (`src/hrono/jobs/worker.py`). Recall is the one synchronous query.
- **Auth.** `Authorization: Bearer <token>`. The dashboard sends the same token
  in the `hrono_token` cookie (HttpOnly, SameSite=Strict). Roles rank
  `reader < writer < admin`. A missing or unknown token is an opaque 401; a
  known user without the role gets 403 (`src/hrono/server/auth.py`). Tokens
  are stored as hashes. The first `serve` on an empty users table mints an
  admin token and prints it once.
- **Errors.** Every failure, including request validation, uses one envelope
  (`src/hrono/server/errors.py`):
  `{"error": {"code": "...", "message": "...", "details": ...}}`.
- **Secrets at rest** are Fernet-encrypted under the master key from
  `--key-file` or `HRONO_MASTER_KEY`, which the server needs to start. Each
  secret row records the `key_id` it was encrypted under. GET masks secrets.
- **Field names** are snake_case. Enum values are kebab-case.

## Health

| Route | Role | Answer |
|---|---|---|
| `GET /health` | none | `{status, database, worker}`; 503 when the database or worker is unusable |
| `GET /version` | none | `{name, version}` |

## Registry collections

`sources`, `connections`, `models`, `prompts`, `trees`
(`src/hrono/registry/collections/`). Every collection has the same routes:

| Route | Role |
|---|---|
| `GET /<collection>` | reader |
| `GET /<collection>/{name}` | reader |
| `POST /<collection>` | writer |
| `PUT /<collection>/{name}[?dry_run=true]` | writer |
| `DELETE /<collection>/{name}` | writer |

Writes are validated before they are stored: a source must be reachable with
its credentials, and a connection must authenticate. A write that fails
validation is refused. `?dry_run=true` applies nothing and returns the impact
on every tree that references the item (`src/hrono/registry/impact.py`). A real
edit marks the affected entities stale and runs nothing. A source edit that
only changes auth leaves nothing stale.

Bodies:

```jsonc
// sources: git | github-user | bitbucket-workspace | confluence | notion
{ "name": "api", "type": "git", "url": "https://github.com/acme/api",
  "auth": { "method": "none" },            // none | token | ssh
  "filter": { "only": ["src/**"], "exclude": ["**/fixtures/**"],
              "include": [], "replace_defaults": false, "max_size_mb": 2 } }
{ "name": "acme-gh", "type": "github-user", "owner": "acme",
  "auth": { "method": "token", "token": "..." },
  "include": ["*"], "exclude": ["*-archive"] }
{ "name": "wiki", "type": "confluence",
  "base_url": "https://acme.atlassian.net/wiki",
  "auth": { "method": "basic", "email": "...", "token": "..." },
  "scope": [{ "type": "space", "key": "ENG" }, { "type": "page", "id": "1" }] }
{ "name": "notes", "type": "notion", "auth": { "method": "token", "token": "..." },
  "scope": [{ "type": "page", "id": "..." }] }

// connections: anthropic | openai | openai-compatible | claude-code
{ "name": "anthropic-main", "provider": "anthropic",
  "auth": { "method": "api-key", "key": "sk-ant-..." }, "endpoint": null }
{ "name": "cc", "provider": "claude-code", "auth": { "method": "none" } }

// models: kind text | embedding; connection null = run in-process
{ "name": "cheap", "kind": "text", "connection": "anthropic-main",
  "model": "claude-haiku-4-5", "role": "condense",   // condense | brief | brief-upper | judge
  "params": { "max_tokens": 4096 }, "price": null }

// prompts: defaults are seeded on first start
{ "name": "condense-default", "role": "condense", "template": "..." }

// trees
{ "name": "backend", "sources": ["api", "wiki"] }
```

The clustering, recall and summarization constants are fixed in code, not
config. See [clustering.md](clustering.md) and
[summarization.md](summarization.md).

## Trees

| Route | Role | Does |
|---|---|---|
| `POST /trees/{name}/maintain` | writer | Cold build: the full pipeline to the root. Returns `{job_id}` |
| `POST /trees/{name}/sync` | writer | Incremental update (`sync-tree`): ingest the diff, place, judge, re-brief, monitor, repair. Returns `{job_id}` |
| `POST /trees/{name}/recall` | reader | `{question, limit=10, pages=false}` → `{hits, message}`; `pages` gives one hit per leaf topic |
| `GET /trees/{name}/export?levels=4` | reader | Rendered agent-facing tree as `{files: [{path, content}], shape}`. `levels` is the hop limit, at least 2 |
| `GET /trees/{name}/export.zip?levels=4` | reader | The same export as a zip archive |
| `GET /trees/{name}/pending` | reader | Incubator pool: sections in no topic yet |
| `GET /trees/{name}/unusable-briefs` | reader | Stored briefs that are model refusals or prompt echoes |
| `GET /trees/{name}/unusable-condensations` | reader | Condensations that are model refusals |

Both `maintain` and `sync` hand back the id of an already queued job for the
same op and tree, so a retry is idempotent.

A recall hit is
`{uri, kind: "source"|"summary", header, body, score, start, end, topic}`.
When nothing is confident, `hits` is empty and `message` says to explore the
map.

### Manual edits

All of these require the admin role (`src/hrono/server/edits.py`). An edit
**pins** what it touches, and the pipeline treats a pin as a hard constraint:
a pinned brief survives re-briefing, and a pinned membership or parent
survives `settle`. `unpin` hands the node back to automation.

| Route | Body |
|---|---|
| `PATCH /trees/{name}/nodes/{id}` | `{title}`: rename a topic |
| `PUT /trees/{name}/nodes/{id}/brief` | `{text}`: override the brief |
| `POST /trees/{name}/nodes/{id}/unpin` | none |
| `POST /trees/{name}/nodes/{id}/reparent` | `{to: <node id>}` |
| `POST /trees/{name}/nodes/merge` | `{ids: [...]}`: the lowest id survives |
| `POST /trees/{name}/nodes/{id}/split` | none |
| `POST /trees/{name}/nodes/{id}/dissolve` | none: members re-enter placement |
| `POST /trees/{name}/sections/{id}/move` | `{to_node}` |
| `POST /trees/{name}/{nodes\|sections}/{id}/notes` | `{text}` |
| `GET /trees/{name}/{nodes\|sections}/{id}/notes` | reader role. Newest first |

Notes appear in the export, so the agent reading the tree sees them.

## Jobs

| Route | Role | Does |
|---|---|---|
| `GET /jobs?op=&status=` | reader | List |
| `GET /jobs/{id}` | reader | One job |
| `GET /jobs/{id}/children` | reader | Child jobs |
| `GET /jobs/{id}/events` | reader | Live progress (Server-Sent Events) |
| `POST /jobs/{id}/cancel` | admin | Cooperative cancel, cascades to children |
| `POST /jobs/{id}/revert` | admin | Undo every change the run made (newest run first, nothing running) |
| `POST /jobs` | admin | `{op, scope, tree}`: enqueue any registered op. For debugging only |

A job is `{id, parent_id, tree, op, scope, status, error, result, started_by,
created_at, updated_at, progress?, cost?}`. Leaf statuses are `pending`,
`running`, `succeeded`, `failed` and `canceled`. A parent's status, progress and
cost are derived from its children, and `partial` is a derived status only.
Running stages out of order through `POST /jobs` can leave a tree that looks
right but is wrong. Use `/sync` instead.

The registered ops (`OPS` in `src/hrono/jobs/ops.py`, filled by each stage
module) are `maintain`, `sync-tree`, `sync`, `split`, `embed`, `cluster`,
`cluster-briefs`, `condense`, `brief`, `brief-upper`, `brief-preview`,
`build-tree`, `update`, `propagate`, `monitor`, `repair`, `settle` and `noop`.
Scope is `{"type": "all"}` (the default) or `{"type": "source", "name": ...}`.
A source-scoped op over all sources fans out into one child job per source.

## Users, usage, admin

| Route | Role | Does |
|---|---|---|
| `GET /users` | reader | List (never tokens) |
| `POST /users` | admin | `{name, role}`. Returns the token once |
| `DELETE /users/{name}` | admin | |
| `GET /usage?by=model&tree=&since=&until=` | reader | Calls, tokens, model time and cost. `by` is `run`, `model`, `upstream-model`, `user` or `day` |
| `POST /admin/rotate-key` | admin | `{old_key, new_key}`. Re-encrypts every secret synchronously; the running server switches keys. Update the key file before the next restart |

## Dashboard

`/ui` is the server-rendered dashboard (`src/hrono/server/ui/`). It uses the
same token and roles as the API, and the server enforces the roles.

## CLI

The CLI is a thin client (`src/hrono/cli.py`, `src/hrono/client/http.py`).
Every client command runs against the current **profile**, stored in
`~/.hrono/config.toml` (or `$HRONO_HOME/config.toml`).

```
hrono serve [--host 127.0.0.1] [--port 8080] [--key-file F] [--db .hrono/hrono.db]
hrono reset [--force] [--db F]                 wipe the local database (lockout recovery)
hrono admin new-key [--out F]                  generate a master key
hrono admin reset-token <user> [--db F]        mint a new token offline

hrono profile add <name> --server URL --token T [--default-tree T]
hrono profile set-token <name> --token T | list | use <name> | current | rm <name>

hrono sources|connections|models|prompts list [--json] | get <name>
                                         | set <name> [-f file.json] | rm <name>
hrono tree config list | get | set | rm        the trees collection

hrono tree maintain <tree>                     cold build
hrono tree sync <tree>                         incremental update
hrono tree export <tree> -o DIR [--levels 4]   write the rendered tree to DIR
hrono tree pending <tree>

hrono recall [TREE] "question" [--limit 10] [--pages] [--json]
hrono jobs list [--op OP] [--status S] [--json] | get <id> | watch <id> | cancel <id>
hrono usage [--by model] [--tree T] [--since YYYY-MM-DD]
```

`set` reads JSON from the file or from stdin and PUTs it. `serve` resolves
`--db` (or `HRONO_DB`) relative to the current directory and keeps the source
clones under `<db parent>/cache/`.
