# hrono — context

## Problem
Knowledge bases for AI agents in enterprise settings: information is scattered across many legacy, non-structured, duplicating subsystems. Giving an agent raw full access is inefficient — it gets lost in unstructured raw data.

## Approach
A hierarchical abstraction tree (raw chunks -> summaries -> summaries of summaries -> root), built from heterogeneous sources (git repos, Contentful, Confluence), that updates incrementally (touch only what changed, not full regeneration).

## prototype/ status
- `hrono.toml` — resource config (currently: git sources only, url + auth = `none`/`ssh`/`env:VAR`).
- `filter.toml` — file filter config: one glob-pattern list (`Path.full_match`, Python 3.13+) covering vendored/generated dirs, known lockfiles, and binary extensions; an oversized-file cap (`max_size_mb`); a null-byte sniff fallback (on/off only, no tunable byte count) for anything a pattern didn't catch.
- `chunking.toml` — maps file extension -> category (code/docs/data), each with `chunk_size_kb` and a recursive-delimiter separator hierarchy. No `chunk_overlap` field — removed after analysis showed a static copied-bytes overlap had no real job (see `prototype/repo-analysis.ipynb`'s conclusion). `chunk_size_kb` values (10/10/2 for code/docs/data) are empirically derived, not guessed — see below.
- `prototype/repo-analysis.ipynb` — the empirical-derivation notebook: clones 4 large open-source repos (Java/Python/TypeScript/Go) as an enterprise-scale proxy, measures file-size distributions per category, finds `chunk_size_kb` via a log-scale Kneedle knee (the point where covering more files stops being worth the extra bytes), and separately investigates `chunk_overlap` — concludes it should be removed entirely (the splitter never truncates a piece, so overlap was solving a problem the separator hierarchy already prevents) and fixes a real reassembly bug it surfaced along the way (raw-char fallback pieces were being joined with a stray `\n` per character). Full reasoning, including the wrong first attempts, is in its final conclusion cell.
- `research.ipynb` — six steps: (1) reads `hrono.toml`, clones/updates each git source into `.hrono/cache/git/<host>/<org>/<repo>/`; (2) reads `filter.toml`, keeps only chunkable files; (3) reads `chunking.toml`, recursively splits each file into chunks, each with a URI (`git://host/org/repo@commit/path#chunk-N`), its byte range in the source file, and a SHA-256 hash of the *raw file bytes* in that range (not the reconstructed chunk text, so it reflects the literal source exactly); (4) reports which files actually needed more than one chunk and prints the real boundary text at each split point; (5) exports `.hrono/chunk_index.json` — references only (`uri`, `byte_start`, `byte_end`, `hash`), no content; (6) groups the index by hash to detect duplicate content across different URIs (e.g. the same repo cloned via two different `hrono.toml` sources) — URI stays the provenance key, hash is the separate dedup key, same split git uses between paths and content-addressed blobs.
- Embeddings (step 8): local via sentence-transformers, model in `embedding.toml` (currently `Qwen/Qwen3-Embedding-0.6B` — multilingual + code, 32k-token input, 1024 dims, Apache 2.0; chosen over API providers since embedding is cheap locally and enterprise chunks shouldn't leave the machine — summarization will need an API regardless). Embedded per unique `hash` into the `embeddings` table keyed `(hash, model)` — content-addressed, incremental (re-runs only embed new hashes), model swap = config edit + auto re-embed. Measured on the dev laptop: ~1.7s/chunk (0.6 chunks/s), so 1M chunks ≈ 19 days locally — prototype-fine, production bulk build needs GPU or API. batch_size lesson: attention memory grows with token count *squared*; batch 32 of 10KB chunks OOM'd an 18GB MPS pool (see `embedding.toml` comments).
- Clustering research (steps 9-16), all on 510 real chunks with a known-group test (webphone's `uk/es/en/translation.json` near-duplicates must cluster together, apart from code):
  - Raw 1024-dim HDBSCAN collapses (one 481-chunk blob) — distance concentration; UMAP reduction is what *creates* the density contrast HDBSCAN needs.
  - Reduced dims barely matter in 12-50 (sweep: near-identical metrics); 25 chosen. The real axis is `eom` (12 clusters, 3-5% noise, but a ~250-chunk frontend mega-cluster survives every dims) vs `leaf` (33-38 clusters sized 5-28 — the "small parents" tree shape — at 24-33% noise).
  - Path-aware similarity per design sketch implemented by concatenation: `[√(1-α)·content_vec ; √α·path_vec]` (path embedded with the same model — ~15 tokens each, negligible cost) makes dot product exactly `(1-α)·content_sim + α·path_sim`, keeping UMAP/ANN pipelines intact (no O(n²) matrix). Finding: path coherence is already 0.92+ at α=0 (semantics≈directories on this corpus); α's real effects are leaf-noise reduction (33%→17% at α=0.5) and breaking the eom mega-cluster at α=0.7.
  - Deterministic reducers (Matryoshka truncation 256/128, random projection, PCA) all lose badly to UMAP (51-79% leaf noise vs 17-33%) — distance-preserving methods keep the flat geometry; UMAP's nonlinear neighbor-pulling is the value, not the dim count. Matryoshka note: truncation = slice + renormalize of stored vectors, supported to 32 dims by Qwen3, useful for storage but doesn't fix clustering.
  - Stability under drift (the core worry for incremental updates): cold full re-fit after 5%-content-change / repo-added reshuffles real structure (ARI ~0.47, cluster survival 0.81-0.85, 15-16% noise flips). Warm-started UMAP (`init=` previous coordinates, new points at nearest neighbor) improves to ARI 0.55-0.59, survival 0.86-0.92, flips 11-14% — rebuilds become "extension-like" but not perfect; residual churn is HDBSCAN boundary decisions. Direction: warm rebuilds + persist coordinates + a diff layer that re-summarizes only nodes whose membership changed; between rebuilds, frozen-transform + incremental assignment per design sketch.
  - Noise strategy (steps 17-18): the step-17 visual diff showed drift churn concentrates at the noise boundary; "noise" is the corpus's most distinctive chunks (no `min_cluster_size` similar siblings), not garbage. Lowering the floor doesn't help — mcs=3 made noise *worse* (22% vs 17%) and mcs=2 degenerates (108 micro-pair clusters). Settled: leaf + mcs=5 + deterministic nearest-member assignment of every noise chunk, computed in the original combined space (reducer-independent, can't flutter). Validated on all 85 noise chunks: similarities 0.57-0.97, median 0.78, even the weakest attachments visibly sane — no distance cap needed at this scale. Result: 0% noise, 37 clusters, sizes 5-29 / median 10. Tree schema should carry an `assigned` flag (density member vs proximity attachment) so summaries can weight cores if needed.
  - Assignment also *stabilizes drift* (step 19, the payoff): comparing total partitions (warm rebuild + assignment) instead of density-cores-only lifts rebuild agreement from ARI 0.55-0.59 to **0.81-0.82** at unchanged survival 0.86-0.92 — the noise-boundary flutter (the largest churn class in the step-17 diff) is absorbed by deterministic attachment rather than converted into cluster-hopping. Residual ~10-15% membership churn per rebuild is the diff layer's job.
  - Update architecture DECIDED and proven (steps 20-23): **updates never re-run the pipeline.** Changed/new chunks are assigned into frozen clusters when best-similarity ≥ TAU=0.70 (in original combined space); chunks below TAU accumulate in a novel pool that is clustered by a *scoped mini-pipeline* (the settled recipe run on just the pool — reproduced the cold rebuild's clusters for the added repo at ARI 0.81, vs 0.55 for agglomerative-threshold alternatives). Guarantees by construction: untouched chunks never move (churn 0 — the project's core requirement); new topics form new clusters instead of polluting old ones (90/91 fmm chunks refused absorption; the 1 absorbed was semantically correct, SecurityConfig→SecurityConfig). Churn anatomy (step 20): full-rebuild churn is mostly whole small clusters merging/splitting with neighbors, not files scattering.
  - Staleness monitor: misfit rate = share of chunks closer to another cluster's centroid than their own (deterministic dot products, cheap, continuous). Order-bias proof (step 23): tree grown purely incrementally (webphone base → +fmm → +octocat) vs cold build of identical data — coherence identical (0.95/0.95), misfit 0.035 vs 0.031 and flat across growth stages (no accumulation), ARI 0.715 (boundaries differ; quality doesn't — "different but equally good"). Policy: run incremental until misfit crosses a threshold, then a warm+diff reconciliation rebuild. Known weak spot: novel pools smaller than min_cluster_size get force-assigned — at scale they should wait in a pending pool until clusterable.

## Storage backend: decided — SQLite + sqlite-vec
Three shapes to hold: flat chunk metadata, a parent/child DAG (multi-parent tree per `design-sketch-v1.md`), and embeddings. Decided on SQLite + `sqlite-vec` in one file (`.hrono/hrono.db`). Deciding argument: at the actual scale (~1M chunks, embeddings ≈ 4-6GB at 1024-1536 dims, internal nodes ≤ N/(b-1) regardless of tree depth) every candidate DB handles the workload, so the pick is the one with zero moving parts — and the incremental update (chunk row + embedding + parent-pointer path) stays one ACID transaction instead of a cross-store consistency problem. Known trade-offs accepted: single writer, no ANN (global similarity scan ~0.5-1s over 1M vectors — not on the main tree-traversal path; bolt on hnswlib later if it hurts), sqlite-vec is young (v0.1.x). Kùzu set aside (Cypher buys nothing at ≤20 indexed hops), Neo4j set aside (server process unjustified).

Implemented so far: `chunks` table (step 7 of `research.ipynb`) — the URI's decomposed parts (`source_type`, `instance`, `path`, `version`, `chunk_no`) are the stored source of truth, `uri` is a STORED generated column (render can't drift from the parts; canonical order `<source-type>://<instance>/<path>#chunk-<n>@<version>` — design-sketch's git example was updated to match its own grammar). `version` is opaque/equality-only across source types; `chunk_no` is a plain integer whose only job is ordering chunks for file reassembly — cross-version chunk identity is `hash` (indexed dedup/embed-once key; named fragments were considered and rejected since `@version` changes every URI on any edit anyway). References only, no content; drop-and-rebuild per run, incremental upsert deferred to the update-mechanism work. `chunk_index.json` still written by step 5; the two coexist for now.

## RAG direction + storage v2 (July 2026) — the second major phase
Decided: alongside agent tree-traversal, hrono gets a **retrieval front-end** (RAPTOR-collapsed-tree-style): embed the user's question, top-k similarity, auto-inject hits with provenance; the agent traverses manually only when that's insufficient. NOT an MCP server (architecture of the client/server split deliberately postponed). This forced a second, finer granularity: **paragraphs** (~200 tokens, the injection unit) vs chunks (~10 KB, the traversal unit).

- **Experiment embedding model decided** (`model-comparison.ipynb`): `ibm-granite/granite-embedding-97m-multilingual-r2` — 11x faster than Qwen3-0.6B (75 vs 835 ms/chunk on the M1, batch 8), clustering quality tied on the model-independent metric (path coherence 0.939 vs 0.947), known-group test passes. Qwen3 stays the final-run model in `embedding.toml`. ARI between the two models' partitions is only ~0.45 — different-but-equally-good trees; never compare partitions across models.
- **Splitting is structure-aware** (cAST-style; naive recursive-delimiter splitting at paragraph scale was tried in `paragraph-split.ipynb` and REJECTED — cuts functions/JSON/prose mid-unit). One mechanism in `structuring.py`, configured by `structuring.toml`: tree-sitter structure tree per file (grammars incl. markdown/json/yaml/toml/xml/groovy); a delimiter cascade (blank-line→line→sentence→comma→word) CONTINUES BUILDING the tree synthetically inside structureless spans; one packer walks it at two budgets (chunks 10 KB greedy, paragraphs 800 B flushing at min_group=100 so decent structural units stand alone); byte-chop only for space-less spans; sub-64 B crumbs merge. Parse+pack ≈ 0.15 ms/file — ~1700x cheaper than embedding.
- **Every span carries `struct_paths`**: a list of full structure paths (one per packed node — several when small siblings share a paragraph), each segment `{type, name?, idx}` with idx from the node's true sibling list; synthetic segments typed `~<delimiter>`; unique per file by construction (verified 0 collisions). Rendered as compact `sp:` URIs (`sp:/ContactService/.class_body/getByUser`; percent-encoded names, `.type` = unnamed, `[i]` only when idx>0) by `structuring.sp_render` — stored in `struct_uris`, so the one-line RAG injection header is just `uri || ' ' || struct_uris`.
- **Storage v2** (`storage-v2.ipynb`, `.hrono/hrono-v2.db`; v1 `hrono.db` untouched as history): `paragraphs` (ground truth; identity parts, `in_chunk`, byte span, hash, struct_paths/struct_uris, virtual fragment-free `uri`) / `chunks` (same shape, materialized product of the same packer — struct_paths NOT derivable from paragraphs', hash includes inter-paragraph gap bytes) / `contents` (content-addressed `hash -> body`; stored in-DB because the git cache only holds the current checkout while rows pin `@version`, and non-git sources can't re-fetch old versions — chunk bodies are NOT duplicated, they reassemble from paragraphs, verified byte-identical corpus-wide). Corpus: 482 files -> 501 chunks -> 4,168 paragraphs (3,898 unique bodies). Schema principles settled along the way: no derivable flag columns (synthetic-ness reads from struct_paths), URIs are fragment-free resource addresses (position is data, not identity), generated columns are VIRTUAL.

## Retrieval recipe: FROZEN (2026-07-25, `rag-retrieval.ipynb`)
Calibrated on 13 prompts (10 answerable + 3 no-answer controls) over the v2 corpus:
**α=0.5 path-blended paragraph vectors (granite-97m) + BM25 (SQLite FTS5 over path+body), qualification Z_VEC ≥ 3.5 solo / keyword z_kw ≥ 6.0 AND vector support z_vec ≥ 3.0 (BM25 never qualifies alone), weighted RRF fusion 70/30 vector/keyword, cap 10; empty set → "no confident matches — traverse the tree".** Strict on purpose: injection costs tokens per request; misses fail safe to traversal (scorecard: controls 2/3 empty, real 8/10 inject with right file #1). Key findings burned in along the way: BM25's z-floor is degenerate solo (legalese outliers); path embedding fixes what bodies don't say (uk-translation, LICENSE); struct paths are neither embedded nor FTS-indexed (names already in bodies); gap-cut adaptive-k rejected as over-aggressive; single-threshold answerability detection is impossible (junk/real z-bands overlap — accepted residual: one control injects 1 hit). Full history + residuals in the notebook's Observations cell.

## The tree: BUILT on v2 (2026-07-25/26)
`tree-build.ipynb` + `.hrono/tree.html`: 501 chunks → 41 level-1 nodes (haiku `l1-pure` gotcha-aware map-reduce over content-hash-cached condensations; all prompts tree-vocabulary-free) → 6 level-2 parents + root (sonnet `v7b-sized` pure-abstraction prompt from the 7-round search in `summarize-level2-experiments.ipynb`: intent-only requirements, free form, no routing — references are mechanical, the LLM never knows it's in a tree). Prompt/model per node + costs in DB; prompt changes auto-invalidate exactly the affected summaries. Faithfulness gate (mechanical) runs in-notebook; accepted finding: models add true expert inferences beyond source in Caution sections (policy: allowed). Node summaries also joined the retrieval index (`rag-summaries.ipynb`): split by the same splitter into the same tables as `node://` sources — architectural questions inject summary paragraphs, detail questions keep hitting source, and the uk-translation retrieval blind spot got fixed by a summary hit.

## Update mechanism: FINAL DESIGN — the relevance cascade (`update-threshold.ipynb`, 6 rounds)
Every similarity metric failed structurally (rounds 1-3: embeddings/Jaccard compare stochastic artifacts) and so did judging summary-vs-summary diffs (round 5: regeneration is FACTUAL SELECTION noise — identical-input pairs judged as changed). Final design, validated round 6 (19/22 case-hop cells unanimous, none/minor line perfectly stable): **hash detects; one universal relevance judge per hop — the change's source diff vs the CURRENT STORED summary one level up ("does anything stated become wrong/incomplete/worth updating?"), both inputs deterministic.** Per cycle: batched per touched node, best-of-3 with ties→max severity; none → recondense only; minor → regen node + parent.drift += 1; major → regen + repeat the judgment against the next ancestor's summary until a hop absorbs it. Attenuation is content-driven and real (test-file removal: major@L1 → none@L2; core deletions/API renames stay major where the parent names them). Drift ≥ 5 forces refresh; membership changes regen the owning node unconditionally (sig); `update_log` records every verdict. ~$0.02/touched node/cycle. Open: D_MAX by judgment; whole flow not yet wired into an end-to-end ingest→upsert→recluster run.

## Edit stability: TESTED, UPDATE rule amended (2026-07-27, `edit-stability.ipynb`)
The lifecycle doc's open point closed: real webphone edit batches (HEAD vs HEAD~3/10/15, incl. a
178-file refactor) replayed through the UPDATE rule against the stored 41-cluster tree. Edits
never orphan chunks (0/216 below TAU) — but the original nearest-member join rule would hop 64%
of edited chunks into adjacent clusters (and misplaces 13% of unchanged chunks in a leave-one-out
control; nearest-centroid: 5%): the churn was the join rule's, not the edits'. Fix ADOPTED into
`clustering-lifecycle.md`'s UPDATE rule: an edited chunk re-checks its own cluster's *stored
pre-batch* centroid first (≥ TAU → stays, only its own summary dirty; pre-batch matters — it
survives the whole-cluster-edited-in-one-batch edge), escapes and brand-new chunks place by
nearest *centroid*. Validated end-to-end: 100% of edited chunks stay (weakest own-sim 0.889),
dirty summaries per batch cut 8→4 / 11→9 / 27→23. Residual: TAU=0.70 was calibrated on
nearest-member sims; centroid sims run lower (fails safe into pending) — re-measure at ~50k.
