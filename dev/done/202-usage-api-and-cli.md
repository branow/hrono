## Context
The ledger (#201) stores calls; a person asks questions of it: what did this run cost, which model is the expensive one, who started the runs that cost the most, how many hours has a model been working.

## Description
`GET /usage` returns roll-ups of the ledger, grouped by one of run, configured model, upstream model, user, or day, filterable by tree and time range. Each group has calls, tokens by kind, model time, and cost. `GET /jobs/{id}` gains the same totals for that run including its children.

Cost: a baked price table per upstream model (input, output, cache-read, cache-write, per million tokens), overridable per model in config. Cost is computed at read time from tokens, so a price correction fixes history.

A provider billed by subscription (`claude-code`) is not a per-token cost. For it, report `billing: subscription` and the API-equivalent figure as an explicit estimate; never add it into a total of real spend. An upstream model with no known price reports cost as unknown, not zero.

`hrono usage [--by run|model|user|day] [--tree] [--since]` prints the same roll-ups. Reader role may read usage.

## Acceptance criteria
- [ ] `GET /usage?by=model` and `by=upstream-model`, `by=run`, `by=user`, `by=day` each return calls, tokens by kind, model seconds and cost
- [ ] a run's totals include every descendant job's calls
- [ ] subscription-billed calls are reported apart from metered spend, labelled as an estimate
- [ ] an unpriced model yields cost unknown and is named, so the operator can add a price
- [ ] `hrono usage` prints a table a person can read without the API docs
- [ ] totals are tested against a ledger written by a real multi-stage run, not rows the test inserted itself

## Out of scope
Budgets, alerts, limits. Dashboard pages (#203).
