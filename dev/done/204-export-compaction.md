## Context
A stored tree can be 20-30 levels deep; an agent should reach a section in at most 3-4 hops. `collapse()` already cuts to N levels by keeping N evenly spaced stored levels and re-parenting across the skipped ones. That bounds depth and says nothing about width: which levels survive is decided by arithmetic on level numbers, so one kept topic can end up listing hundreds of children, and a page an agent cannot scan is as bad as a hop too many. It has only ever been run on trees of 2-3 levels, where it does nothing.

## Description
Make compaction a deliberate trade of depth for width.

Inputs: a hop limit (default 4, floor 2) and a per-page width budget (a baked constant with its evidence, the number of children one index page may list).

Choose the kept levels by the resulting shape, not by even spacing: among the selections that satisfy the hop limit, prefer the one whose widest page is smallest. When no selection fits the width budget, keep the hop limit and say so in the result — the export reports its own shape (levels, pages per level, widest page) so the caller can see what it got.

An index page lists each child with its title and a one-line summary taken from the child's brief, so an agent can choose a branch without opening it.

Deterministic, pure, no LLM call: the same stored tree and options give byte-identical output.

PO question, flagged rather than guessed: when a page still exceeds the budget at the hop limit, do we accept the wide page (proposed) or add a hop? The ticket implements "accept and report" unless the user rules otherwise.

## Acceptance criteria
- [ ] a synthetic stored tree of 25 levels exports to at most the hop limit, for limits 2, 3 and 4
- [ ] every stored section is reachable from the root in the export — none dropped by a skipped level
- [ ] level selection is by resulting width: a test tree where even spacing gives a 300-child page and another selection gives 40 picks the second
- [ ] index pages list children with title and one-line summary
- [ ] the result reports levels, pages per level and the widest page
- [ ] a tree already within the hop limit exports unchanged from today's output
- [ ] same input, same bytes — asserted over two runs
- [ ] `hrono tree export --levels` keeps working; the new options have the same names in the API and the CLI

## Out of scope
Writing new briefs for merged levels (no LLM in export). The panel (#205). Agent testing (#206).
